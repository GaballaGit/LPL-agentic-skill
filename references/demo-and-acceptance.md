# Demo and acceptance guide

## Credible handoff

Require a complete journey with visible persisted results, reproducible local run, fabricated fixtures, reset procedure, and evidence-backed value explanation. Provide focused verification results and clear boundaries around mocks/external systems. Adapt to the actual event requirements.

## Acceptance examples

For an onboarding exception prototype, adapt these examples; they are not real account-opening policy:

1. Given an incomplete synthetic packet, show the missing item, illustrative rule, and source field.
2. Assign/correct the issue; persist and reload its changed state.
3. Reject another demo tenant's direct API reads and mutations.
4. Reject duplicate or stale approval without a second completion event.
5. Record the transition and recover from an unavailable optional provider.

For a developer-tool track, use a concrete service failure, affected advisor journey, synthetic telemetry, and verified recovery. Make financial context meaningful.

## Three-minute demo

| Time | Show | Evidence |
| --- | --- | --- |
| 0:00–0:25 | Persona, trigger, friction | Synthetic scenario and public priority |
| 0:25–1:40 | Complete main journey | Working UI/API/persistence and changed outcome |
| 1:40–2:15 | Trust/recovery control | Actual denial, approval check, audit event, or fallback |
| 2:15–2:45 | Value and architecture | Observed metric and one decision |
| 2:45–3:00 | Integration path and limit | Simulated boundary and next verifiable step |

Rehearse from reset. Keep a labeled recording/screenshots if event rules permit fallback. Do not present seeded or recorded results as live integration.

## Measurement

Use a reproducible baseline. Compare steps/time on the same fixture, naming who performed it and number of runs. For issue detection, report labeled expected/detected/missed cases. For recovery, name the injected fault and observed interval.

Separate observations, modeled business impact, and targets. A five-case synthetic evaluation supports that evaluation, not production performance.

## Judge-facing explanation

Explain user value, sourced LPL relevance, distinction from existing offerings, controls, and integration seam. Show infrastructure evidence that exists.

Prepare concise answers: Why this problem? Why this stack? What exists already? Where is authorization enforced? What happens on retries/outages? Which integrations are mocked? What would production require? What was measured?
